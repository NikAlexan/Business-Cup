## 1. Подсветка слов — сделано (sherpa-onnx на бэкенде)

Web Speech API ненадёжен (Chrome/Linux молчит, в Firefox его нет). WASM в браузере
отброшен: npm-билд `sherpa-onnx` собран с NODERAWFS и в браузере не запускается,
а модель с рантаймом весят ~58 МБ на клиент. Запись и так уходит на сервер для
анализа, поэтому распознавание тоже на сервере.

- `WS /api/v1/speech-follow?rate=…`: Origin и cookie гостя проверяются до accept;
  кадры float32 моно (≤ 1 с), на каждый ответ `{"text"}`; звук не сохраняется;
  лимит — `max_recording_seconds`. Без модели сокет закрывается (1011), фронт
  показывает обычный текст.
- Модель `sherpa-onnx-streaming-zipformer-en-2023-06-26` int8 (~73 МБ, Apache-2.0),
  качается в `scripts-download-vad.py` с sha256 при сборке образа. Маленькая 20M
  теряла начало фраз; эта ~22× быстрее реального времени на 1 поток (≈20 записей на ядро).
- Фронт: AudioWorklet → чанки по 100 мс на родной частоте (ресемплирует сервер),
  очередь до открытия сокета. `followWords`: префикс 3+ букв, склейка разбитых слов
  («to day»), ре-якорь по двум словам подряд, если начало не расслышано.
- Прослушивание записи тоже подсвечивает: сервер отдаёт `{"words": [[слово, старт_с]]}`
  (время из таймстампов токенов), хук хранит их за запись, `RecorderDock` сообщает
  `audio.currentTime` каждый кадр. На стопе досылается 0.6 с тишины, чтобы дошли последние
  слова; на `ended` показывается весь услышанный текст (хвост webm короче потока на ~0.3 с).
- Проверено: pytest (сокет, отказ без cookie и с чужим Origin, битый кадр), vitest,
  прогон в Chrome с подменой микрофона на flite-WAV — подсвечен весь текст.
- Не сделано: лимит одновременных сокетов; 48 кГц float32 — ~190 КБ/с вверх
  (даунсэмпл в worklet, если важен мобильный трафик). Живым голосом не проверено.

## 2. Сквозной прогон в Chrome

На `localhost:8080`, ширины 390 / 820 / 1280, скриншоты против `design/screens/`:

- новая сессия → запись → анализ → профиль → занятие → перезагрузка на
  `/exercise/:id`, `/done/:id`, `/analyzing` → прогресс → (DEMO_MODE) проверка;
- отказ в микрофоне (подсказки MicBlocked), тихая запись (`needs_rerecord`),
  `failed` анализа с причиной и «Try again»;
- запись до лимита — автостоп, запись сохраняется;
- двойной клик по Finish / Complete / Use this take — один запрос;
- 401 без cookie на любой странице кроме `/` → `/`;
- 409 (`lesson_locked`, `plan_item_already_completed`) — текст из `message`;
- PWA: манифест без ошибок, SW активен, в Cache Storage нет `/api`, Lighthouse installable.

## Открытые вопросы

- E06: метка целевого темпа остаётся? (Запись в оценке теперь без времени.)
- Снять ли серверный лимит длительности записи (`protocol.json`, `MAX_RECORDING_SECONDS`).
- Разминки с таймером (E01) требуют минимальное время на сервере — оставить.

## Принятые решения (для ревью)

- Награды пишутся в попытку при засчёте; минуты self_confirmation — из
  `estimated_duration_seconds` пункта (= каталог).
- Тесты бэкенда — в образе `business-cup-backend` + dev-зависимости (без uv/venv).
- Только `screens.css` из дизайна: токены в нём, `components.css` не используется.
- Последнее упражнение ведёт на `/done/:id`, который делает идемпотентный
  `PUT /progress` — один путь, безопасен при перезагрузке.
- Высоты столбиков волны — декоративная форма макета; данные — цвет/состояние.
- Progress: последние измерения плитками, без графика темпа (в API нет ряда).
- CheckIn — входной экран; сравнение — в Profile повторной оценки; график контура
  высоты тона из макета не сделан (нет данных в `comparison`).
- Баннер обновления только в AppShell, не на экранах записи.
- Тесты `api.ts`/`format.ts` писались вместе с кодом, не RED первыми.
