# Контракт Voice Training API v1

Контракт по ТЗ v2 от 14.11.2026. Бэкенд реализован в `app/`; запуск и проверки описаны в корневом README. Примеры в коллекции — статические демонстрационные данные, а не результаты реального анализа. Точные значения ID, текстов, измерений и состава плана генерируются сервером.

## Файлы и импорт

- `Voice-Training.postman_collection.json` — Postman Collection v2.1: 46 запросов, 120 примеров успешных ответов и ошибок.
- `Voice-Training.postman_environment.json` — окружение с URL и ID для примеров.

Импортировать оба JSON через Import, выбрать окружение `Voice Training — local / mock`. Для будущего локального API оставить `base_url=http://localhost:8000`, `api_prefix=/api/v1`.

Для разработки без бэкенда создать в Postman Mock Server на основе этой коллекции, подставить его URL в `base_url`. Выбирать конкретный ответ заголовком `x-mock-response-name`, например `200 — completed initial` или `200 — empty dashboard` (имя взять из Examples нужного запроса). Для private mock потребуется `x-api-key`, ключ не коммитить. Mock возвращает статические примеры: он не хранит прогресс, не запускает задачи, не проверяет cookie, не удаляет данные и не проигрывает настоящее аудио. Для воспроизводимых mock-сценариев использовать исходные ID окружения и адреса примеров. Автосохранение ID из ответов рассчитано прежде всего на настоящий API.

Cookie авторизации браузерного фронта на моках не проверяются; Postman Mock Server не заменяет локальную проверку cookie/CORS. Поддержка mock-запросов multipart зависит от выбранного режима сопоставления: при разработке UI можно подменять транспорт загрузки статическим ответом из Examples.

## Зафиксированные решения

- Без регистрации, bearer-токенов и оплаты. Серверная гостевая сессия в `guest_session` cookie, `HttpOnly; SameSite=Lax; Path=/`, `Secure` при HTTPS. `guest_id` и `subject_id` — информационные идентификаторы, не способ авторизации.
- Контрольная оценка — три отдельных файла: контрольный текст, новый текст и интонация. До 60 секунд каждый, до 180 секунд суммарно. При проблеме заменяется только нужная запись.
- Только завершённые занятия и серия дней; без XP, монет и рейтингов — по ответу заказчика.
- Английские задания и сообщения, `locale=en-US`. Документация интеграции — на русском.
- Один план содержит 14 последовательных занятий. Правило MVP: не более одного завершённого занятия за местную календарную дату; пропуски не сдвигают индекс задания и не аннулируют план. Это уточнение исходного ТЗ.
- Контрольная проверка открывается через 14 **календарных дней**, а не после 14 пройденных занятий. Дата считается от последней успешной оценки в текущем IANA timezone пользователя.
- Новый успешный контроль создаёт новую версию плана. Старые планы/попытки остаются в истории.
- Первичная оценка не требует ожидания. `reassessment.available` относится только к повторной оценке.

## Актуальные упражнения

В каталоге `catalog-v6` — 12 типов по 24 варианта. Статические Examples коллекции показывают прежние демонстрационные тексты; для реальной практики использовать snapshot `plan_item.task`, включая `repetitions`, `reflection_prompt`, `timing` и `verification`. Подробности: [контракт упражнений](../docs/improvements/exercise-contract.md).

Рекомендуемые время и темп не блокируют завершение. Новые разминки — self-confirmation. Для записей анализируется пригодность аудио; отклонение темпа и недоступное измерение дают coaching. При настроенном провайдере после сохранения пригодного аудио запускается отдельный фоновый речевой разбор; его результат не влияет на зачёт. `estimated_duration_seconds` включает подготовку и прослушивание и не является фактическим временем. Для untimed self-confirmation время неизвестно и не начисляется как фактическое.

Для дополнительного дубля завершённого упражнения передать `practice_only=true` и при multipart-загрузке, и при сохранении попытки. Нужна новая запись; исходный дубль переиспользовать нельзя. Наград и повторного завершения нет, фактическая длительность нового пригодного аудио учитывается один раз. Для untimed self-confirmation длительность остаётся неизвестной. Новые запросы коллекции показывают этот путь; `extra_recording_id` хранится отдельно от исходной записи. У каждого нового POST должен быть новый Idempotency-Key.

## Порядок интеграции

1. `POST /guest-session` → сохранить cookie автоматически. Выбор цели и согласие передаются здесь. Если cookie уже есть, запрос возобновляет сессию, не сбрасывая данные. `GET /me` позволяет восстановить UI после перезагрузки.
2. `POST /assessments` с `kind=initial` → draft, три задания с точными текстами и `task_id`.
3. Для каждого задания `POST /recordings` multipart с `file`, `purpose=assessment`, `assessment_id`, `task_id`. В Postman выбрать настоящий файл вручную. Для второй/третьей записи поменять `task_id` на `{{task_novel_id}}` / `{{task_intonation_id}}`.
4. На каждую загрузку получить HTTP 202 + `job_id`, опрашивать `GET /jobs/{job_id}` по `poll_after_ms`, обычно раз в 2 секунды. Один `quality_job_id` в окружении перезаписывается каждой загрузкой: завершать их последовательно либо хранить все ID на фронте.
5. После трёх успешных проверок `POST /assessments/{id}/submit` → 202 и отдельный `assessment_job_id`. Это запускает полный анализ, ИИ-разбор и создание плана. До submit можно заменять записи; после submit состав записей блокируется.
6. После завершения задачи `GET /assessments/{id}` → метрики/разбор, `GET /plan` → все 14 занятий. `GET /today` — источник текущего занятия.
7. По `plan_item.task.verification.type`: `timer` → передать `elapsed_seconds`; `self_confirmation` → `self_confirmed=true`; `recording` → загрузить аудио упражнения, дождаться лёгкой проверки, передать `recording_id`. Все варианты сохраняются через `POST /exercise-attempts`.
8. Успешная попытка завершает элемент занятия. Когда завершены все элементы, `PUT /progress/{lesson_id}` с `{"status":"completed"}` завершает занятие и обновляет серию. ID в этом маршруте — **ID занятия**, не упражнения.
9. `GET /progress` → статистика, активность по датам, история измерений и аудио. `GET /assessments` → история оценок. `GET /plans/{id}` → в том числе архивный план.
10. В разрешённую дату создать оценку с `kind=reassessment`; повторить протокол. Результат содержит `comparison`, ссылки «до/после» и новый `plan_id`.

Не запускать всю коллекцию автоматически через Runner как E2E: она содержит альтернативные сценарии, контрольную проверку до разрешённой даты и **удаление всех данных**. Запрос self-confirmation применим только к реально выданному элементу с соответствующим способом проверки; пример плана не содержит E02, поэтому его переменная специально не заполнена.

## Общие структуры и правила

Полные JSON-запросы/ответы находятся в Body и Examples каждого запроса. Публичные ID — непрозрачные UUID-строки, время — RFC 3339 UTC, календарные даты — `YYYY-MM-DD`. Числа измерений — JSON number. Отсутствующее значение — `null`, не ноль.

`goal`: `clear_speech | expressive_voice | confident_delivery`. Теги каталога: `articulation, clarity, pace, pauses, intonation, expressiveness, breath, delivery`.

Задача: `queued | processing | completed | needs_rerecord | failed`. `GET /jobs` по ID возвращает HTTP 200 даже для проваленной задачи; статус задачи находится внутри JSON. При terminal-статусе `poll_after_ms=null`, опрос прекращается. `type`: `recording_check | assessment_analysis | exercise_review`. `result` различается по типу и состоянию; в Examples есть каждый вариант. `stage` — текстовый этап, не обещание линейного процента готовности.

Оценка: `draft | queued | processing | completed | needs_rerecord | failed`. Запись: `queued | processing | completed | needs_rerecord | failed`. План: `active | archived | completed`. Занятие: `locked | available | in_progress | completed`. Элемент занятия: `pending | completed`. Попытка: `passed | needs_retry`; завершение неудачной попытки обозначено `completed_at=null`.

До завершения оценки `report`/`plan_id` равны null, а `measurements`, `comparison`, `analysis_metadata`, `recordings` могут отсутствовать. После завершения первичной оценки `comparison=null`; после повторной — объект сравнения. При непригодности исходной записи задачей возвращаются ID для перезаписи. При провале провайдера ошибка находится в `job.error`, без выдуманного отчёта.

Пример численной метрики:

```json
{"available": true, "value": 142.6, "unit": "words/min", "unavailable_reason": null}
```

Недостоверная метрика:

```json
{"available": false, "value": null, "unit": "Hz", "unavailable_reason": "insufficient_voiced_audio"}
```

В assessment-v2 темп, паузы, высота и диапазон интонации измеряются по двум первым текстам (control_text и novel_text). Третий текст с интонационными контрастами передаётся аудиомодели для слуховых наблюдений и не входит в эти численные измерения. Привязки указаны в `measurement_scope`. Диапазон F0 — p10/p90 валидных кадров. `pause_ratio` и clipping — доли 0..1. График F0 — массив `points` с `time_seconds` от начала контрольной записи; `value=null` на неозвученных участках. Для сравнения передаются before/after/delta, но при несопоставимости delta=null. Рост/падение числа автоматически не означает улучшения.

Каталог содержит общие варианты. Для показа конкретного упражнения фронт использует **`plan_item.task`**, где уже зафиксированы версия, текст, инструкция, тип проверки и ограничения. Не выбирать случайный вариант заново на фронте. `example.audio_url=null` допустим: текстовый пример не обещает синтезированное аудио.

### Идемпотентность

Каждый POST требует заголовок `Idempotency-Key` с UUID. **Перед каждой новой логической операцией вручную менять `idempotency_key` в Postman**, в том числе перед загрузкой следующего задания, новой попыткой и новой оценкой. При сетевом повторе сохранять тот же ключ и payload. На фронте генерировать UUID один раз при создании операции и хранить до получения ответа. Не генерировать новый UUID на каждую повторную отправку.

Сервер хранит ключ в рамках гостевой сессии + HTTP method + path, минимум 24 часа. Повтор с тем же ключом и тем же payload возвращает исходный статус/тело, с другим payload — 409 `idempotency_conflict`. Для файлов сравнивается хеш содержимого и поля формы. Начальное создание сессии также защищается ключом даже до появления cookie; повтор выдаёт ту же сессию. Для DELETE естественная идемпотентность означает отсутствие повторного эффекта, но повтор после удаления cookie может вернуть 401.

`PUT /progress` идемпотентен по самому ID занятия. У submit, retry и завершения занятия дополнительно есть защита от конкурентных вызовов с разными ключами. Worker записывает полный отчёт и план атомарно и проверяет, что сессия не удалена.

### Ошибки

```json
{
  "error": {
    "code": "reassessment_not_available",
    "message": "Your next assessment is available on November 28.",
    "details": {"next_available_on": "2026-11-28", "timezone": "America/New_York"},
    "request_id": "f8895f3d-03ad-5e71-9b63-245dc41ffda6"
  }
}
```

Все HTTP-ошибки, включая validation FastAPI, нужно нормализовать к этой форме. UI ветвится по `error.code`, а не по английскому message. Базовые коды:

| HTTP | code | Действие UI |
|---|---|---|
| 401 | `session_required` | Создать новую сессию; прежние данные не восстанавливаются |
| 403 | `demo_mode_disabled` / `origin_not_allowed` | Не использовать операцию / исправить origin |
| 404 | `not_found` / `plan_not_found` | Ресурс недоступен / сначала пройти оценку |
| 409 | `reassessment_not_available` | Показать серверную дату следующей проверки |
| 409 | `assessment_not_ready` / `recording_not_ready` | Дождаться проверки или дозаписать задания |
| 409 | `assessment_in_progress` | Продолжить текущую оценку |
| 409 | `assessment_locked` / `recording_check_in_progress` | Дождаться текущей обработки |
| 409 | `idempotency_conflict` | Новый ключ только для действительно новой операции |
| 409 | `lesson_incomplete` / `lesson_locked` / `daily_lesson_limit` | Показать незавершённые задания или дату открытия |
| 409 | `plan_item_already_completed` / `plan_inactive` | Обновить состояние плана |
| 413 | `file_too_large` | Записать меньший файл |
| 415 | `unsupported_audio_format` | Выбрать поддерживаемый MediaRecorder MIME |
| 416 | `range_not_satisfiable` | Повторить запрос аудио без неверного Range |
| 422 | `validation_error` / `consent_required` / `assessment_duration_exceeded` | Исправить ввод / согласие / длительность |
| 429 | `rate_limit_exceeded` | Учитывать `Retry-After` в секундах |
| 503 | `service_not_ready` | Показать временную недоступность |

Остальные предметные ошибки приведены рядом с запросами. Коды причин качества: `no_speech`, `too_short`, `too_long`, `clipping`, `excessive_noise`, `decode_failed`, `insufficient_voiced_audio`. Некачественный декодируемый файл обрабатывается через `needs_rerecord`; неверный контейнер может быть отклонён немедленно с 415. Бюджет и частотные лимиты задаёт сервер, фронт не зашивает числа.

### Браузер и приватное аудио

Для отдельного origin фронта использовать `fetch(..., {credentials: 'include'})` на всех API-запросах. Бэкенд должен разрешить конкретный origin через credentialed CORS. На MVP рекомендуются один origin либо локальные порты одного hostname; смешивать `localhost` и `127.0.0.1` не нужно. Независимые cross-site домены с `SameSite=Lax` этим контрактом не поддерживаются.

Для изменяющих запросов сервер проверяет browser Origin по allowlist; запросы без Origin (Postman) допускаются с действительной сессией. Cookie не читается JavaScript. Не передавать guest ID как авторизацию или делать аудио публичным.

`audio_url` — относительный путь к API, его разрешать относительно **origin API**, а не origin фронта. Для надёжного credentialed воспроизведения можно получить Blob через fetch и создать object URL. Поддерживается byte Range; бинарное тело в Postman Examples — заглушка, не аудиофайл.

## Demo и оплата

`GET /me` отдаёт `demo_mode` и `reassessment.demo_override_available`. Только при DEMO_MODE сервер принимает `demo_override=true` для повторной оценки. Отчёт всегда содержит `analysis_metadata.demo` с признаками обхода даты и подготовленных данных. UI явно помечает демонстрацию. Это не доказательство улучшения за две недели. Импорт подготовленной истории в текущий публичный API не добавлен; для демонстрации выбран обход даты.

Stripe test mode интегрирован из main: checkout, подписанный webhook и Customer Portal. При `BILLING_PROVIDER=none` MVP доступен без оплаты; при `stripe_test` права ежедневной практики определяются сохранённым статусом подписки в `/me`. `exercise_coaching` также учитывает доступ и наличие AI-конфигурации. Billing-запросы описаны отдельно в [контракте Stripe](../design/stripe-test-mode.md); текущая Postman-коллекция содержит упражнения и основной assessment-поток.

## Проверка артефактов

JSON и структура коллекции проверяются отдельно от работающего бэкенда. В Postman добавлены проверки допустимого HTTP-статуса и общего формата HTTP-ошибок, а также сохранение ID в environment. Они помогают ручной интеграции, но не заменяют E2E и не доказывают реализацию API.

### Особенности реализации MVP

`GET /today` может показать завершённое сегодня занятие из архивного плана, если контрольная оценка уже создала новый план: новый день откроется завтра. `plan_id` в этом ответе соответствует показанному занятию; текущий план — в `GET /plan`.

Ежедневные проверки не запускают полный ИИ-разбор. Для E06 вызывается отдельная расшифровка и проверяется целевой диапазон WPM; при неподтверждённой расшифровке или выходе из диапазона попытка получает `needs_retry`. В остальных ежедневных упражнениях темп без расшифровки недоступен.

Для повреждённого файла после успешной загрузки `quality.duration_seconds`, `speech_seconds` и `clipping_ratio` могут быть null. Тело `GET /jobs/{id}` дополнительно содержит `retry_batches` для ограниченных ручных повторов. Оценка содержит `demo_override_used` для аудита; задание может дополнительно содержать технические `pending_recording_id` и `last_upload_id`.


## Восстановление и цикл повторной практики

`GET /plan-items/{id}` возвращает исходное задание и занятие даже из архивного плана. `pending_take` содержит последний незавершённый дубль текущего режима: `recording_id`, `job_id`, `practice_only`, `status` и сохранённый фокус. После reload продолжить polling этого job и сохранить попытку с данным recording_id. После сохранения попытки дубль исчезает из pending. Приложение не восстанавливает файл, который ещё не был принят сервером.

`PUT /recordings/{id}/dismiss` с `{}` идемпотентно исключает незавершённый дубль из восстановления. Это не удаление аудио. Сохранённые в истории дубли исключить нельзя. Сохранять попытку с dismissed-дублем нельзя.

`PUT /exercise-attempts/{id}/reflection` с `{"note":"…"}` сохраняет субъективное наблюдение пользователя (до 500 символов); повтор того же текста не меняет дату. Пустой текст очищает заметку. Для следующего дополнительного дубля можно передать `based_on_attempt_id` в multipart и JSON попытки. Сервер сохраняет снимок фокуса при upload, поэтому поздняя правка исходной заметки не меняет историю нового дубля.

Новые задания E06 и E08 используют необязательные таймкоды транскрипции для темпа и пауз. `feedback.scope=quality_and_timing`, версия `speech-timing-feedback-v1`, содержат `insights`, цитату/интервал для прослушивания и `next_step`. Это описание тайминга, не оценка произношения или выразительности. При недоступных метриках пригодное аудио сохраняется с `audio_quality_only`. За пределами длины файла, при пересечениях интервалов или несовпадении количества слов метрики недоступны. Новая версия измерений baseline/check-in — `voice-metrics-v3`; старые измерения не дают числового сравнения с новыми.

`me.data_provenance.prepared_demo_history` постоянно обозначает подготовленную историю, включая период после настоящих записей. Подготовленная оценка не считается сопоставимым baseline. `comparison.audio_pairs` содержит только пары реально существующих записей; Profile показывает их плееры «до/после».


## Фоновый речевой разбор

Пригодный записанный дубль сначала сохраняется как `passed`, получает однократный зачёт и возвращает `speech_review` со статусом `queued` либо `unavailable`. Job типа `exercise_review` сохраняет результат в той же попытке; качество исходной записи, notes и время не меняются. Polling работает через обычный `/jobs/{id}`; после terminal job перечитать `/exercise-attempts/{id}`. Reload восстанавливает job из сохранённой попытки.

`POST /exercise-attempts/{id}/review` с `{}` и новым Idempotency-Key может запросить разбор старого дубля или дубля со статусом unavailable. Уже существующий queued/processing/completed/failed job не дублируется. Для retryable failed использовать `/jobs/{id}/retry` с обычными конечными лимитами повторов.

Версия `exercise-review-v1`: `report.summary`, одно `observation` либо null, `next_step`, `listening_question`, `limitations`. Источник — `audio_model`, а не объективная оценка навыка. Модель выбирает цитату и номер её вхождения; backend привязывает её к проверенным словесным таймкодам фактической транскрипции. Произвольные временные метки от модели не принимаются. Недостоверные тайминги дают unavailable, отсутствующая цитата не публикуется. Субъективная интерпретация слышимого может ошибаться — UI предлагает проверить её прослушиванием.

При отсутствии конфигурации, исчерпании лимита или ошибке разбора исходная практика остаётся сохранённой. Настройки: `EXERCISE_REVIEWS_ENABLED=true`, `MAX_EXERCISE_REVIEWS_PER_DAY=10` (на гостя), `MAX_TOTAL_EXERCISE_REVIEWS_PER_DAY=100` (на UTC-день сервиса). Лимиты считают jobs, не доллары и не количество вызовов внутри bounded retry. Быстрые проверки качества имеют приоритет перед ожидающими фоновыми jobs; уже запущенный job не прерывается.


## Восстановление baseline/check-in и отмена upload

`GET /assessments/{id}` добавляет в каждый task `pending_take`: последний принятый сервером, но ещё не завершивший проверку дубль (`recording_id`, `job_id`, `status`). Упавшая проверка остаётся восстанавливаемой после очистки `pending_recording_id`: используется `last_upload_id`. Для старых записей без `check_job_id` сервер находит собственный recording-check job. После принятой/отклонённой проверки `pending_take=null`; качество и ID находятся в основных полях task. Повтор failed job выполняется через `/jobs/{id}/retry`, без повторной отправки файла. Ошибка polling отображается отдельно. Файл до приёма сервером не восстанавливается.

`PUT /recording-uploads/{upload_key}/cancellation` с `{"plan_item_id":"UUID"}` отменяет незавершённую дополнительную загрузку. `upload_key` — UUID из Idempotency-Key исходного upload, а не новый ключ отмены. Коллекция запоминает его перед загрузкой. Этот PUT идемпотентен без отдельного Idempotency-Key. Если upload уже сохранён, сервер исключает его из восстановления; если ещё нет — сохраняет намерение отмены и отклоняет поздний upload с `409 upload_canceled`. Операции сериализуются с upload по гостевой сессии. Историю сохранённых попыток отмена не удаляет. Повтор ключа с другим упражнением даёт конфликт; чужое/незавершённое упражнение недоступно. Незавершённые отмены без принятой загрузки ограничены дневным лимитом записей гостя.

UI не считает отмену подтверждённой при сетевой ошибке и предлагает повторить её. До подтверждения отмены поздний результат проверки не создаёт попытку. После подтверждения серверное состояние защищает от восстановления отменённого дубля при reload.

Перед check-in показываются сохранённые условия предыдущей завершённой оценки и подставляются расстояние, комната и заметки; микрофон определяется заново. На экране записи показываются условия исходного assessment. Это помогает повторить setup и не изменяет уже сохранённый контракт записи. Протокол повторяет контрольный и интонационный текст, а незнакомый текст обновляет.


SQLite: и API, и worker начинают транзакцию записи через BEGIN IMMEDIATE до первого чтения изменяемого JSON. PostgreSQL использует блокировки строк. Даже если старый worker уже потерял dismissed_at, отдельный маркер отмены исключает дубль из pending и сохранения attempt. На клиенте намерение отмены сохраняется до отправки запроса и проверяется перед восстановлением job после reload; подтверждение или удаление гостевых данных очищает его. В локальном хранилище находятся только ID операции/записи и области гостя/задания, не аудио. Если браузер блокирует хранилище, текущая страница удерживает намерение в памяти и при сетевой ошибке просит не закрывать её до подтверждения.


## Перенос навыка в рассказ и следующее занятие

После прослушивания пригодной записи `POST /practice-focus` принимает `source_attempt_id`, `note` (1–500 символов после trim) и необязательный `skill`. Источник должен быть собственной passed-попыткой с аудио; self-confirmation не подходит. Операция атомарно сохраняет reflection источника и новую неизменяемую версию фокуса. Навыки и вопросы рубрики возвращаются в `GET /practice-focus`; там же находится последний `last_check` для активной версии. Число смен фокуса ограничено дневным лимитом записей. Для реального API заменить `focus_source_attempt_id` ID записанного дубля, а не разминки.

Новый фокус показывается в E12 перед записью и на Today, включая следующий день. При старте записи фронт фиксирует именно показанную версию и отправляет её UUID как необязательное multipart-поле `training_focus_id`. Поле в Postman по умолчанию отключено: включать только для narration и соответствующего `recording_plan_item_id`. Без поля фокус автоматически не прикрепляется. Изменение фокуса в другой вкладке, его очистка или последующая правка reflection не переписывают начатый/сохранённый дубль. Принятый upload, pending_take и attempt сохраняют `training_focus` целиком.

После прослушивания рассказа `PUT /exercise-attempts/{story_attempt_id}/focus-check` сохраняет `outcome`: `heard | partly | not_yet | unsure`. Ответ помечен `source=user_listening`; он не является оценкой модели/независимого слушателя, не доказывает освоение и не меняет награды, время или план. Один и тот же outcome возвращается без изменения timestamp. Сравнение дублей показывает, если у них были разные фокусы.

`DELETE /practice-focus/{id}` очищает только совпадающий активный указатель; повтор старого DELETE не сбрасывает более новый выбор. Исторические snapshots остаются. Доступ к исходным записям сохраняет обычные проверки владельца. Удаление всех гостевых данных удаляет и фокусы.

При неполных внутренних таймкодах Whisper общий темп может остаться доступным, если крайние опоры, число слов и границы аудио надёжны. Паузы и articulation rate тогда имеют `unavailable_reason=word_alignment_incomplete`; они не интерполируются. Цитата AI-разбора может использовать более широкий достоверный фрагмент с `evidence.note`. `speech_review.prompt_version` фиксирует версию инструкций модели. Подробности ограниченной проверки настоящего API — [журнал оценки](../docs/improvements/evaluations/README.md).


## Сохранённый анализ и ограничения профиля

`assessment.job_id` восстанавливает полный анализ после reload, даже если сохранённая ссылка содержит только `assessment_id`. При `failed` повторять `/jobs/{job_id}/retry`, если `retryable=true`; не делать повторный submit или upload. UI показывает серверный `stage`, ошибки polling и отсутствие ID; незавершённый профиль перенаправляет к сохранённой операции, а не показывает пустой результат. Просроченный кэш профиля обновляется перед решением о возврате к обработке.

После completed доступны исходные приватные записи и сохранённый `measurement_scope`, ограничения `report.limitations` и `comparison.limitations`. Для novel_text пары сравниваются разные незнакомые тексты, а не идентичные слова. В assessment-v2 все численные измерения относятся к первым двум чтениям; интонационное задание дополнительно слушает модель. Новые запросы модели отделяют системные инструкции от недоверенного аудио/контекста и фиксируют `analysis_metadata.prompt_version=assessment-coaching-v2`. Это версия инструкций, не гарантия точности суждения.

Фокус narration имеет приоритет над заметкой предыдущего дубля в контексте коучинга: `training_focus.note` и его рубрика описывают одну цель; `practice_focus` остаётся контекстом истории. В targets-v2 диапазоны чисел прежние, но подписи доли пауз больше не утверждают корректность их смыслового расположения. Старые сохранённые подписи на фронте также исправлены; `voice-metrics-v3` и сопоставимость чисел не меняются.


## Решение после прослушивания

`PUT /exercise-attempts/{id}/reflection` принимает `note` (до 500 символов) и необязательный `intent`: `experiment | keep | undecided`. Это решение пользователя, не подтверждение модели или оценка навыка. Поле можно сохранить с пустой заметкой, в том числе для undecided. Если intent не передан или равен `null`, прежнее значение сохраняется; для отложенного решения передать `undecided`. Совпадающие note/intent не меняют updated_at. Награды, время и зачёт не зависят от решения.

`POST /practice-focus` принимает необязательный `intent=experiment|keep`. При пропуске наследует решение исходной заметки; для старых данных без intent использует experiment. Если источник помечен undecided, нужен явный новый выбор, иначе `422 focus_intent_required`. `keep` получает шаги переноса удачного приёма без обязательного усиления. `undecided` сохраняет только заметку, не заменяя текущий фокус; UI это явно поясняет и даёт перейти к управлению текущей целью. Rubric version — story-listening-v2, старые snapshots сохраняются.

Намерение замораживается внутри training_focus вместе с историей рассказа; обычный повтор сохраняет его в practice_focus при приёме upload. Редактирование исходной заметки потом не меняет сохранённый дубль. Worker передаёт practice_intent отдельно от текста заметки. Exercise-coaching-v3 содержит инструкции для сохранения удачного и отложенного решения; это не доказательство соблюдения инструкции моделью. Прежние реальные v1/v2 ответы в журнале оценки не переписываются.

Новый UI предлагает выбор намерения и собственную заметку, без прямого копирования next_step в цель. Идея AI остаётся видимой как необязательная подсказка рядом с исходным аудио. Обычное завершение и повтор доступны без заполнения reflection. Старый POST с прежним Idempotency-Key и без intent воспроизводит исходный ответ: новое необязательное поле не меняет прежний fingerprint.

## Необязательное аудиосравнение и выбранная граница E08

`GET /plan-items/{id}` возвращает `listening_example` (публичный синтетический пример), `listening_boundaries` из сохранённого текста задания и последнюю собственную `listening_plan`. Эти поля не меняют выданное задание. У остальных типов пример/план могут быть `null`, список границ пустым.

`POST /plan-items/{id}/listening-plan` принимает `example_id`, `answer=a|b|unsure` и целочисленный `boundary_index` из списка. Ответ 201 — отдельный неизменяемый снимок примера, границы и исходных слов. Выбор не оценивается и не начисляет время/ноты/завершение. Для сетевого повтора сохранить Idempotency-Key; изменённый выбор — новая операция. Чужое задание или snapshot недоступны с 404. Неприменимый пример/граница — 422. Количество сохранений за местный день ограничено `max_uploads_per_day`.

Перед началом записи зафиксировать показанную версию, затем явно передать её `listening_plan_id` в multipart `/recordings`. Отсутствие поля означает отсутствие выбранной границы у дубля: сервер не подставляет последний выбор автоматически. Snapshot сохраняется в `recording.listening_plan`, `pending_take.listening_plan` и принятой `attempt.listening_plan`; последующие выборы и обновление каталога его не переписывают. Фронт восстанавливает незавершённый дубль с его собственным снимком.

Повтор POST с прежним ключом возвращает исходный неизменяемый receipt, даже если другая вкладка уже сохранила новый выбор. После receipt перечитать `/plan-items/{id}`, чтобы показать актуальную `listening_plan`; не присваивать receipt полю текущего выбора без сверки. Если чтение не удалось, повторить ту же операцию с прежним ключом. Новая `pending_take`, обнаруженная при обновлении уже открытого экрана, также требует восстановления её сохранённого job и собственного snapshot; текущую локальную запись/Blob при этом не подменять. После завершения проверки передавать в attempt контекст именно проверенного дубля, включая источник дополнительной практики.

`feedback.planned_pause` — необязательный описательный результат `planned-boundary-v1`: `available`, `gap_seconds`, `source=transcript_timing`, `evidence={quote,start_seconds,end_seconds}` либо причина недоступности. Число означает промежуток между двумя распознанными словами в найденном локальном контексте, а не оценку смыслового расположения. Совпадение соседнего контекста, таймкоды и пределы записи проверяются; неоднозначная фраза/неточная расшифровка/сбой ASR дают unavailable без отказа в зачёте пригодного аудио. При нескольких чтениях переход относится к первому надёжно найденному совпадению; номер прохода не определяется. Источник остаётся личным аудио с cookie-авторизацией. Публичные `/practice-examples/...` содержат только подготовленные синтетические примеры; они отделены от API и личных записей.

## Решение пользователя и следующий шаг речевого разбора

Завершённый `speech_review.report` содержит `intent_policy_version=listening-decision-v1`, `action_intent`, `action_source` и `observation_status`. В `next_step` и `listening_question` применяется сохранённое решение для следующей практики: `keep` сохраняет выбранный признак без усиления, `undecided` предлагает переслушать текущую запись перед выбором изменения. `action_source=user_listening_decision` обозначает этот детерминированный шаг; при `experiment`/отсутствии решения источник — `audio_model`, и идея остаётся необязательной. Исходные предложения модели сохранены отдельно в `model_next_step` и `model_listening_question`.

Приоритет будущего шага — поздняя сохранённая `reflection.intent`, затем замороженное намерение `training_focus`/`practice_focus`. Это не меняет историческую цель дубля. Worker перечитывает решение перед публикацией; сохранение поздней reflection заново применяет правило к завершённому отчёту без нового анализа/наград. Повтор того же PUT идемпотентен. Для старых отчётов без метаданных клиент применяет такое же правило к отображению. Запоздалый GET не должен заменять более новое сохранённое решение.

`observation_status=hypothesis` означает непроверенное слуховое впечатление AI, даже если цитата привязана к записи. Корректность цитаты доказывает место прослушивания, а не правоту модели. Числовые измерения остаются отдельными данными; правило намерения не объявляет слуховые суждения достоверными. Новые raw-пробы и offline-воспроизведение опубликованы в [диагностике](../docs/improvements/evaluations/README.md).


### Конкурирующие правки заметки

Сохранённая `reflection` содержит целочисленный `revision`; отсутствие поля у старых данных означает `0`. PUT reflection принимает необязательный `expected_revision`, POST practice-focus — `expected_reflection_revision`. Передавайте версию исходной заметки, полученную из GET attempt. Если она изменилась и запрос меняет содержимое, сервер возвращает `409 reflection_changed` с `error.details.current_attempt` (только своему владельцу). Ни заметка, ни активный фокус при этом не перезаписываются. Совпадающий текст/intent можно повторить с прежней версией: это не создаёт новую revision или updated_at. Пропуск/null оставляет старое безусловное поведение для прежних клиентов.

При изменении только текста UI отправляет note и expected_revision, без повторной отправки intent. Нетронутые поля следуют актуальной записи; конфликтующие черновики остаются до явного выбора сохранённого варианта или своего черновика. Версия растёт при изменении note/intent; исправление отображения/политики AI само по себе её не увеличивает. Исторические training_focus, practice_focus и выбранная граница дубля остаются замороженными.

Старый Idempotency-Key POST practice-focus воспроизводит неизменяемый receipt, включая прежнюю source_attempt. Это не текущий указатель: после receipt клиент читает GET practice-focus и GET source attempt и сверяет версии. Необязательное поле проверки версии при пропуске не меняет fingerprint прежних запросов.

### Сравнение собственных дублей A/B

`POST /exercise-attempts/{id}/comparison` с `{}` и Idempotency-Key создаёт или открывает сравнение пригодного повторного дубля с его замороженным `practice_focus.attempt_id`. Оба дубля должны принадлежать гостю, содержать принятое аудио и относиться к одному plan item. Для одной упорядоченной пары сервер сохраняет один порядок A/B; повторное открытие с новым ключом не меняет порядок. Лимит применяется к созданию новых пар; существующую можно открыть после его исчерпания.

`GET /listening-comparisons/{id}` возвращает актуальную пару. До ответа clips содержит только label и приватный audio_url; после — ещё role (`previous|current`) и attempt_id. Первый POST возвращает 201, повторное открытие — 200. Старый receipt по прежнему ключу неизменяем: после него читать GET, чтобы не скрыть уже сохранённый ответ.

`PUT /listening-comparisons/{id}/result` принимает `choice=a|b|no_clear_difference|unsure` и необязательный `note` до 500 символов. Первый ответ сохраняется атомарно с раскрытием подписей; точный повтор не меняет saved_at. Изменить его после раскрытия нельзя (`409 comparison_already_answered`); новые мысли можно сохранить в обычной reflection. Это личное впечатление, а не оценка произношения, независимое слепое исследование или доказательство улучшения.

`GET /listening-comparisons/{id}/audio/{a|b}` передаёт исходное аудио через обычные ownership/Range-проверки, без redirect на ID записи. Доступ требует cookie владельца, включая запросы диапазона; ответ private, no-store, поддерживается 206/416. Пара сохраняет исходный текст/вопрос/фокус, доступна после reload и архивирования плана. Подготовка и ответ не дают наград, минут, зачёта или изменения уровня и не вызывают AI-провайдера. Пользователь может узнавать собственную речь; скрываются подписи внутри окна, а не вся информация о его записях.
