# Контракт Voice Training API v1

Контракт по ТЗ v2 от 14.11.2026. Бэкенд реализован в `app/`; запуск и проверки описаны в корневом README. Примеры в коллекции — статические демонстрационные данные, а не результаты реального анализа. Точные значения ID, текстов, измерений и состава плана генерируются сервером.

## Файлы и импорт

- `Voice-Training.postman_collection.json` — Postman Collection v2.1: 32 запроса, 88 примеров успешных ответов и ошибок.
- `Voice-Training.postman_environment.json` — окружение с URL и ID для примеров.

Импортировать оба JSON через Import, выбрать окружение `Voice Training — local / mock`. Для будущего локального API оставить `base_url=http://localhost:8000`, `api_prefix=/api/v1`.

Для разработки без бэкенда создать в Postman Mock Server на основе этой коллекции, подставить его URL в `base_url`. Выбирать конкретный ответ заголовком `x-mock-response-name`, например `200 — completed initial` или `200 — empty dashboard` (имя взять из Examples нужного запроса). Для private mock потребуется `x-api-key`, ключ не коммитить. Mock возвращает статические примеры: он не хранит прогресс, не запускает задачи, не проверяет cookie, не удаляет данные и не проигрывает настоящее аудио. Для воспроизводимых mock-сценариев использовать исходные ID окружения и адреса примеров. Автосохранение ID из ответов рассчитано прежде всего на настоящий API.

Cookie авторизации браузерного фронта на моках не проверяются; Postman Mock Server не заменяет локальную проверку cookie/CORS. Поддержка mock-запросов multipart зависит от выбранного режима сопоставления: при разработке UI можно подменять транспорт загрузки статическим ответом из Examples.

## Зафиксированные решения

- Без регистрации, bearer-токенов и оплаты. Серверная гостевая сессия в `guest_session` cookie, `HttpOnly; SameSite=Lax; Path=/`, `Secure` при HTTPS. `guest_id` и `subject_id` — информационные идентификаторы, не способ авторизации.
- Контрольная оценка — три отдельных файла: контрольный текст, новый текст и интонация. До 60 секунд каждый, до 180 секунд суммарно. При проблеме заменяется только нужная запись.
- Только завершённые занятия и серия дней; без XP, монет и рейтингов — по ответу заказчика.
- Английские задания и сообщения, `locale=en-US`. Документация интеграции — на русском.
- Один план содержит 14 последовательных занятий. Правило MVP: не более одного завершённого занятия за местную календарную дату; пропуски не сдвигают индекс задания и не аннулируют план. Это уточнение исходного ТЗ.
- Контрольная проверка открывается через 14 **календарных дней**, а не после 14 пройденных занятий. Дата считается от последней успешной оценки в текущем IANA timezone пользователя.
- Новый успешный контроль создаёт новую версию плана. Старые планы/попытки остаются в истории.
- Первичная оценка не требует ожидания. `reassessment.available` относится только к повторной оценке.

## Актуальные упражнения

В каталоге `catalog-v5` — 12 типов по 24 варианта. Статические Examples коллекции показывают прежние демонстрационные тексты; для реальной практики использовать snapshot `plan_item.task`, включая `repetitions`, `reflection_prompt`, `timing` и `verification`. Подробности: [контракт упражнений](../docs/improvements/exercise-contract.md).

Рекомендуемые время и темп не блокируют завершение. Новые разминки — self-confirmation. Для записей анализируется пригодность аудио; отклонение темпа и недоступное измерение дают coaching. Полный ИИ-разбор каждого ежедневного упражнения пока не реализован. `estimated_duration_seconds` включает подготовку и прослушивание и не является фактическим временем. Для untimed self-confirmation время неизвестно и не начисляется как фактическое.

Для дополнительного дубля завершённого упражнения передать `practice_only=true` и при multipart-загрузке, и при сохранении попытки. Нужна новая запись; исходный дубль переиспользовать нельзя. Наград и повторного завершения нет, фактическая длительность нового пригодного аудио учитывается один раз. Для untimed self-confirmation длительность остаётся неизвестной. Новые запросы коллекции показывают этот путь; `extra_recording_id` хранится отдельно от исходной записи. У каждого нового POST должен быть новый Idempotency-Key.

## Порядок интеграции

1. `POST /guest-session` → сохранить cookie автоматически. Выбор цели и согласие передаются здесь. Если cookie уже есть, запрос возобновляет сессию, не сбрасывая данные. `GET /me` позволяет восстановить UI после перезагрузки.
2. `POST /assessments` с `kind=initial` → draft, три задания с точными текстами и `task_id`.
3. Для каждого задания `POST /recordings` multipart с `file`, `purpose=assessment`, `assessment_id`, `task_id`. В Postman выбрать настоящий файл вручную. Для второй/третьей записи поменять `task_id` на `{{task_novel_id}}` / `{{task_intonation_id}}`.
4. На каждую загрузку получить HTTP 202 + `job_id`, опрашивать `GET /jobs/{job_id}` по `poll_after_ms`, обычно раз в 2 секунды. Один `quality_job_id` в окружении перезаписывается каждой загрузкой: завершать их последовательно либо хранить все ID на фронте.
5. После трёх успешных проверок `POST /assessments/{id}/submit` → 202 и отдельный `assessment_job_id`. Это запускает полный анализ, ИИ-разбор и создание плана. До submit можно заменять записи; после submit состав записей блокируется.
6. После завершения задачи `GET /assessments/{id}` → метрики/разбор, `GET /plan` → все 14 занятий. `GET /today` — источник текущего занятия.
7. По `plan_item.task.verification.type`: `timer` → передать `elapsed_seconds`; `self_confirmation` → `self_confirmed=true`; `recording` → загрузить аудио упражнения, дождаться лёгкой проверки, передать `recording_id`. Все варианты сохраняются через `POST /exercise-attempts`.
8. Успешная попытка завершает элемент занятия. Когда завершены все элементы, `PUT /progress/{lesson_id}` с `{"status":"completed"}` завершает занятие и обновляет серию. ID в этом маршруте — **ID занятия**, не упражнения.
9. `GET /progress` → статистика, активность по датам, история измерений и аудио. `GET /assessments` → история оценок. `GET /plans/{id}` → в том числе архивный план.
10. В разрешённую дату создать оценку с `kind=reassessment`; повторить протокол. Результат содержит `comparison`, ссылки «до/после» и новый `plan_id`.

Не запускать всю коллекцию автоматически через Runner как E2E: она содержит альтернативные сценарии, контрольную проверку до разрешённой даты и **удаление всех данных**. Запрос self-confirmation применим только к реально выданному элементу с соответствующим способом проверки; пример плана не содержит E02, поэтому его переменная специально не заполнена.

## Общие структуры и правила

Полные JSON-запросы/ответы находятся в Body и Examples каждого запроса. Публичные ID — непрозрачные UUID-строки, время — RFC 3339 UTC, календарные даты — `YYYY-MM-DD`. Числа измерений — JSON number. Отсутствующее значение — `null`, не ноль.

`goal`: `clear_speech | expressive_voice | confident_delivery`. Теги каталога: `articulation, clarity, pace, pauses, intonation, expressiveness, breath, delivery`.

Задача: `queued | processing | completed | needs_rerecord | failed`. `GET /jobs` по ID возвращает HTTP 200 даже для проваленной задачи; статус задачи находится внутри JSON. При terminal-статусе `poll_after_ms=null`, опрос прекращается. `type`: `recording_check | assessment_analysis`. `result` различается по типу и состоянию; в Examples есть каждый вариант. `stage` — текстовый этап, не обещание линейного процента готовности.

Оценка: `draft | queued | processing | completed | needs_rerecord | failed`. Запись: `queued | processing | completed | needs_rerecord | failed`. План: `active | archived | completed`. Занятие: `locked | available | in_progress | completed`. Элемент занятия: `pending | completed`. Попытка: `passed | needs_retry`; завершение неудачной попытки обозначено `completed_at=null`.

До завершения оценки `report`/`plan_id` равны null, а `measurements`, `comparison`, `analysis_metadata`, `recordings` могут отсутствовать. После завершения первичной оценки `comparison=null`; после повторной — объект сравнения. При непригодности исходной записи задачей возвращаются ID для перезаписи. При провале провайдера ошибка находится в `job.error`, без выдуманного отчёта.

Пример численной метрики:

```json
{"available": true, "value": 142.6, "unit": "words/min", "unavailable_reason": null}
```

Недостоверная метрика:

```json
{"available": false, "value": null, "unit": "Hz", "unavailable_reason": "insufficient_voiced_audio"}
```

Измерения темпа/пауз/высоты относятся к контрольному тексту; диапазон интонации — к заданию на интонацию. Привязки указаны в `measurement_scope`. Диапазон F0 — p10/p90 валидных кадров. `pause_ratio` и clipping — доли 0..1. График F0 — массив `points` с `time_seconds` от начала контрольной записи; `value=null` на неозвученных участках. Для сравнения передаются before/after/delta, но при несопоставимости delta=null. Рост/падение числа автоматически не означает улучшения.

Каталог содержит общие варианты. Для показа конкретного упражнения фронт использует **`plan_item.task`**, где уже зафиксированы версия, текст, инструкция, тип проверки и ограничения. Не выбирать случайный вариант заново на фронте. `example.audio_url=null` допустим: текстовый пример не обещает синтезированное аудио.

### Идемпотентность

Каждый POST требует заголовок `Idempotency-Key` с UUID. **Перед каждой новой логической операцией вручную менять `idempotency_key` в Postman**, в том числе перед загрузкой следующего задания, новой попыткой и новой оценкой. При сетевом повторе сохранять тот же ключ и payload. На фронте генерировать UUID один раз при создании операции и хранить до получения ответа. Не генерировать новый UUID на каждую повторную отправку.

Сервер хранит ключ в рамках гостевой сессии + HTTP method + path, минимум 24 часа. Повтор с тем же ключом и тем же payload возвращает исходный статус/тело, с другим payload — 409 `idempotency_conflict`. Для файлов сравнивается хеш содержимого и поля формы. Начальное создание сессии также защищается ключом даже до появления cookie; повтор выдаёт ту же сессию. Для DELETE естественная идемпотентность означает отсутствие повторного эффекта, но повтор после удаления cookie может вернуть 401.

`PUT /progress` идемпотентен по самому ID занятия. У submit, retry и завершения занятия дополнительно есть защита от конкурентных вызовов с разными ключами. Worker записывает полный отчёт и план атомарно и проверяет, что сессия не удалена.

### Ошибки

```json
{
  "error": {
    "code": "reassessment_not_available",
    "message": "Your next assessment is available on November 28.",
    "details": {"next_available_on": "2026-11-28", "timezone": "America/New_York"},
    "request_id": "f8895f3d-03ad-5e71-9b63-245dc41ffda6"
  }
}
```

Все HTTP-ошибки, включая validation FastAPI, нужно нормализовать к этой форме. UI ветвится по `error.code`, а не по английскому message. Базовые коды:

| HTTP | code | Действие UI |
|---|---|---|
| 401 | `session_required` | Создать новую сессию; прежние данные не восстанавливаются |
| 403 | `demo_mode_disabled` / `origin_not_allowed` | Не использовать операцию / исправить origin |
| 404 | `not_found` / `plan_not_found` | Ресурс недоступен / сначала пройти оценку |
| 409 | `reassessment_not_available` | Показать серверную дату следующей проверки |
| 409 | `assessment_not_ready` / `recording_not_ready` | Дождаться проверки или дозаписать задания |
| 409 | `assessment_in_progress` | Продолжить текущую оценку |
| 409 | `assessment_locked` / `recording_check_in_progress` | Дождаться текущей обработки |
| 409 | `idempotency_conflict` | Новый ключ только для действительно новой операции |
| 409 | `lesson_incomplete` / `lesson_locked` / `daily_lesson_limit` | Показать незавершённые задания или дату открытия |
| 409 | `plan_item_already_completed` / `plan_inactive` | Обновить состояние плана |
| 413 | `file_too_large` | Записать меньший файл |
| 415 | `unsupported_audio_format` | Выбрать поддерживаемый MediaRecorder MIME |
| 416 | `range_not_satisfiable` | Повторить запрос аудио без неверного Range |
| 422 | `validation_error` / `consent_required` / `assessment_duration_exceeded` | Исправить ввод / согласие / длительность |
| 429 | `rate_limit_exceeded` | Учитывать `Retry-After` в секундах |
| 503 | `service_not_ready` | Показать временную недоступность |

Остальные предметные ошибки приведены рядом с запросами. Коды причин качества: `no_speech`, `too_short`, `too_long`, `clipping`, `excessive_noise`, `decode_failed`, `insufficient_voiced_audio`. Некачественный декодируемый файл обрабатывается через `needs_rerecord`; неверный контейнер может быть отклонён немедленно с 415. Бюджет и частотные лимиты задаёт сервер, фронт не зашивает числа.

### Браузер и приватное аудио

Для отдельного origin фронта использовать `fetch(..., {credentials: 'include'})` на всех API-запросах. Бэкенд должен разрешить конкретный origin через credentialed CORS. На MVP рекомендуются один origin либо локальные порты одного hostname; смешивать `localhost` и `127.0.0.1` не нужно. Независимые cross-site домены с `SameSite=Lax` этим контрактом не поддерживаются.

Для изменяющих запросов сервер проверяет browser Origin по allowlist; запросы без Origin (Postman) допускаются с действительной сессией. Cookie не читается JavaScript. Не передавать guest ID как авторизацию или делать аудио публичным.

`audio_url` — относительный путь к API, его разрешать относительно **origin API**, а не origin фронта. Для надёжного credentialed воспроизведения можно получить Blob через fetch и создать object URL. Поддерживается byte Range; бинарное тело в Postman Examples — заглушка, не аудиофайл.

## Demo и оплата

`GET /me` отдаёт `demo_mode` и `reassessment.demo_override_available`. Только при DEMO_MODE сервер принимает `demo_override=true` для повторной оценки. Отчёт всегда содержит `analysis_metadata.demo` с признаками обхода даты и подготовленных данных. UI явно помечает демонстрацию. Это не доказательство улучшения за две недели. Импорт подготовленной истории в текущий публичный API не добавлен; для демонстрации выбран обход даты.

Stripe API, checkout и webhook отсутствуют. `subject_id` выдаётся в `/me` для будущей интеграции, `capabilities` показывает права. Бэкенд проверяет внутренний `AccessPolicy.check_access(subject_id, capability)`, в MVP `NoBillingAccessPolicy` разрешает доступ. Это внутренняя точка расширения, не публичный endpoint изменения прав.

## Проверка артефактов

JSON и структура коллекции проверяются отдельно от работающего бэкенда. В Postman добавлены проверки допустимого HTTP-статуса и общего формата HTTP-ошибок, а также сохранение ID в environment. Они помогают ручной интеграции, но не заменяют E2E и не доказывают реализацию API.

### Особенности реализации MVP

`GET /today` может показать завершённое сегодня занятие из архивного плана, если контрольная оценка уже создала новый план: новый день откроется завтра. `plan_id` в этом ответе соответствует показанному занятию; текущий план — в `GET /plan`.

Ежедневные проверки не запускают полный ИИ-разбор. Для E06 вызывается отдельная расшифровка и проверяется целевой диапазон WPM; при неподтверждённой расшифровке или выходе из диапазона попытка получает `needs_retry`. В остальных ежедневных упражнениях темп без расшифровки недоступен.

Для повреждённого файла после успешной загрузки `quality.duration_seconds`, `speech_seconds` и `clipping_ratio` могут быть null. Тело `GET /jobs/{id}` дополнительно содержит `retry_batches` для ограниченных ручных повторов. Оценка содержит `demo_override_used` для аудита; задание может дополнительно содержать технические `pending_recording_id` и `last_upload_id`.
